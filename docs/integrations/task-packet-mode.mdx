title: "Task Packet Mode API"
description: "Phase 1 REST and MCP documentation for Vibe Kanban Task Packet Mode."
---

Task Packet Mode lets Vibe Kanban compile one issue into one Task Packet Protocol v1 document, dispatch that packet to a local coding agent run, and ingest one Result Envelope for review.

<Info>
Phase 1 is a headless single-packet flow. The adapter manifest reports `max_packets_per_parent_run: 1` and `transport: local-vibe-execution`.
</Info>

## Overview

Task Packet Mode has two surfaces:

- REST endpoints under `/api` for project configuration, packet persistence, run inspection, and result ingestion
- MCP tools on the Vibe Kanban MCP server for compile-and-dispatch, parent-run inspection, and Result Envelope submission

All examples on this page use Task Packet Protocol v1 with `schema_version: 1`.

## Project orchestration configuration

Before you can dispatch packets for a project, configure Task Packet Mode for that remote project.

### Configuration fields

| Field | Type | Required | Notes |
|------|------|------|------|
| `local_project_id` | UUID | Yes | Local Vibe Kanban project linked to the remote project |
| `enabled` | boolean | Yes | Enables or disables Task Packet Mode for the project |
| `profile` | string | Yes | Used as the packet `project.id` and `stack`; must be non-empty |
| `executor_config` | object | Yes | Coding agent selection, for example `{"executor":"CODEX"}` |
| `in_progress_status_id` | UUID or `null` | No | Remote issue status to apply after dispatch starts |
| `review_status_id` | UUID or `null` | No | Remote issue status to apply after a `complete` result |
| `repository_mappings` | array | Yes | At least one mapping is required |

Each repository mapping must contain:

| Field | Type | Required | Notes |
|------|------|------|------|
| `logical_id` | string | Yes | Packet repository identifier |
| `repo_id` | UUID | Yes | Local repository record used for workspace creation |
| `role` | string | Yes | Must be `primary` or `supporting` |
| `target_branch` | string | Yes | Branch checked out for local execution |
| `read_paths` | array of strings | Yes | Scope entries copied into `scope.read` |
| `write_paths` | array of strings | Yes | Scope entries copied into `scope.write` |
| `forbidden_paths` | array of strings | Yes | Scope entries copied into `scope.forbidden` |

### Task packet persistence

These endpoints store and inspect validated protocol documents directly. They are useful for integrations, diagnostics, and tests.

| Method | Path | Purpose |
|------|------|------|
| `GET` | `/api/task-packets` | List all stored task packets |
| `POST` | `/api/task-packets` | Persist one schema-valid Task Packet Protocol v1 packet |
| `GET` | `/api/task-packets/{task_packet_id}` | Fetch one stored task packet by database ID |
| `GET` | `/api/task-packets/{task_packet_id}/results` | List all stored result envelopes for that packet |
| `POST` | `/api/task-packets/{task_packet_id}/results` | Persist one schema-valid Result Envelope for that packet |

`POST /api/task-packets` accepts:

```json
{
  "issue_id": "optional UUID",
  "workspace_id": "optional UUID",
  "execution_process_id": "optional UUID",
  "packet": { "schema_version": 1 }
}
```

`POST /api/task-packets/{task_packet_id}/results` accepts:

```json
{
  "execution_process_id": "optional UUID",
  "workspace_id": "optional UUID",
  "result": { "schema_version": 1 }
}
```

<Tip>
The server validates both packet and result payloads against Task Packet Protocol v1 and rejects duplicate `packet_id` values.
</Tip>

### Issue compilation and local dispatch

These endpoints drive the Phase 1 orchestration flow.

| Method | Path | Purpose |
|------|------|------|
| `GET` | `/api/issues/{issue_id}/task-packet-runs` | List parent runs for an issue |
| `POST` | `/api/issues/{issue_id}/task-packet-runs` | Compile one packet, create one local workspace execution, and return run details |
| `GET` | `/api/task-packet-runs/{parent_run_id}` | Inspect one parent run, its packet run, stored packet, and submitted result |
| `POST` | `/api/packet-runs/{packet_run_id}/result` | Submit the single Result Envelope for a packet run |

`POST /api/issues/{issue_id}/task-packet-runs` accepts:

```json
{
  "kind": "documentation",
  "acceptance": [
    "Every Phase 1 REST endpoint is documented.",
    "Return one schema-valid Result Envelope through submit_task_packet_result."
  ]
}
```

The compiled packet uses:

- `schema_version: 1`
- `packet_id: "{issue.simple_id}-r{revision}"`
- `project.id` and `stack` from the orchestration `profile`
- `project.repositories` and `scope` entries derived from `repository_mappings`
- `agent_requirements.constraints.transport: "local-vibe-execution"`

If dispatch succeeds, the response includes:

- `parent_run`: the orchestration record for the issue revision
- `packet_runs`: the single Phase 1 packet run
- `packet`: the compiled Task Packet Protocol v1 document
- `result`: `null` until a Result Envelope is submitted

### Result Envelope submission

`POST /api/packet-runs/{packet_run_id}/result`

This endpoint accepts exactly one Result Envelope for the packet run. The server rejects the request if:

- `workspace_id` is missing
- `workspace_id` does not match the packet run's workspace
- `result.execution.orchestrator.run_id` does not match `packet_run_id`
- the Result Envelope is not Task Packet Protocol v1 valid
- a result was already submitted for that run

<Warning>
The run ID check is strict. `execution.orchestrator.run_id` must equal the packet run UUID, not the parent run UUID.
</Warning>

## MCP tools

Task Packet Mode exposes three MCP operations on the Vibe Kanban MCP server.

| Tool | Purpose | Required parameters |
|------|------|------|
| `compile_issue_to_packets` | Compile one issue into one validated packet and dispatch it to a local execution | `issue_id` |
| `get_parent_run` | Fetch one parent run, its packet run, packet, and result | `parent_run_id` |
| `submit_task_packet_result` | Submit the single schema-valid Result Envelope for a packet run | `packet_run_id`, `result` |

### `compile_issue_to_packets`

This tool calls `POST /api/issues/{issue_id}/task-packet-runs` and forwards optional `kind` and `acceptance` values.

```json
{
  "issue_id": "88888888-8888-8888-8888-888888888888",
  "kind": "documentation",
  "acceptance": [
    "Every Phase 1 REST endpoint is documented.",
    "All three Task Packet MCP operations are documented."
  ]
}
```

### `get_parent_run`

This tool calls `GET /api/task-packet-runs/{parent_run_id}`.

```json
{
  "parent_run_id": "77777777-7777-7777-7777-777777777777"
}
```

## Complete headless execution example

<Steps>

```bash
curl -X PUT 'http://localhost:3000/api/projects/11111111-1111-1111-1111-111111111111/orchestration' \
  -H 'Content-Type: application/json' \
  -d '{
    "local_project_id": "22222222-2222-2222-2222-222222222222",
    "enabled": true,
    "profile": "vibe-kanban",
    "executor_config": {"executor": "CODEX"},

        "logical_id": "vibe-kanban",
```

</Step>

```json MCP
    "kind": "documentation",
```
